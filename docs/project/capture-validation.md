## 自动恢复、重复点播与可选编码修复

2026-11-14，在上述已记录问题基础上继续修复。下列结果取代前一节“长断线后需要人工重播”的限制；AV1 经用户明确确认留作后续。

### 实现

- 实时 Feed 保留用户的观看意图。断流或临时离线释放旧观看会话并以 1/2/4/8/10 秒退避重试；恢复后重新建立国标点播与浏览器连接。手动停止、切换通道、退出页面取消请求和重试，权限错误不循环重试，录像回放不自动从头开始。
- 每个新观看会话使用新视频元素；同一 MediaStream 的音视频 track 到达时不重复赋值 srcObject。结束时关闭旧 PeerConnection、WebCodecs、HLS 和协商请求，迟到事件不能将已关闭会话标成播放中。
- 播放推进按 `totalVideoFrames - droppedVideoFrames` 判断，避免解码/接收计数增长但未呈现画面时被误判为正常。实时断流不再终止观看意图。
- USB 端心跳或注册失败时取消旧媒体会话，避免网络恢复后的新 INVITE 被旧会话占用。
- 客户端加入实际采集能力枚举、分辨率/帧率/码率/编码下拉框、H.265 编码、HEVC AUD 分帧及 PS map 0x24；H.264 保留 0x1b。

### 修改配置后的启动操作

修正“表单有改动就禁用启动按钮”的交互：现在显示可用的「保存并启动设备」，按顺序保存、再启动。真实浏览器验证修改码率后直接启动成功；端口设为 0 时明确提示范围错误且 running=false；改回有效端口后保存并启动成功，最终恢复原 1500kbps、H.265 配置并已向线上平台注册。保存失败不会使用旧配置悄悄启动。

### UDP 监听与首次注册竞态修复

进一步定位此前的 `listen udp ... bind`：端口由设备端自身监听占用，ServeUDP 尚未将 socket 放入 sipgo 共享传输池时，首次 REGISTER 尝试再次绑定同一端口。现在等待传输层进入首次读取（此时已登记共享 socket）后才注册，不采用固定 sleep，也不依赖 5 秒失败重试。

真实 socket 的注册/目录/注销测试每次连续启动 5 轮，整组重复执行 3 次，均未出现 bind 日志；全仓 Go 测试通过。本机更新后保留用户当前配置，首次启动同一秒即注册线上平台成功，日志只有“正在注册/注册成功”，15062 端口仅由新版客户端持有。

FFmpeg 的 `Last message repeated N times` 表示前一条相同日志被合并计数，不能单独视作 N 次设备故障；需结合前一条日志和设备实际状态判断。

### 1080p30 H.265 编码积压排查（2026-11-15）

同一真实 USB 摄像头、1920×1080、30fps、20000kbps，逐项运行 240 帧空输出基准，不保存视频。采集直通约 29.78fps，解码与 full→limited 转换约 29.80fps；原 x265 `pools=2:frame-threads=2` 仅约 22.16fps（0.739x），确认编码阶段无法实时处理。8 个工作线程、单帧线程约 29.79fps；RTX 4080 SUPER 的 HEVC NVENC 对照约 29.76fps。上述帧率均包含真实摄像头的实时采集上限，不能当作编码器最大吞吐量。

修正软件编码参数：工作线程池使用 `min(8, CPU 数)`，至少 1；`frame-threads=1` 避免多帧并行引入额外帧等待。仍使用 libx265，尚未实现客户端显卡编码选择。保留用户原始画质配置，更新本机客户端并恢复线上注册与播放。

完整采集→编码→PS/RTP→公网发送实测 10.02 秒约 29.75fps、18.43Mbps；线上浏览器约 10.11 秒新增 302 帧，约 29.87fps，丢弃帧计数保持 25，区间零新增丢弃帧。全仓 Go 测试通过。这证明该样本恢复实时吞吐，不等同于测得端到端延迟，也不能排除其他网络与播放缓冲影响。
